No sensitive effect without a permit.

Wrapbox is the runtime authorization layer for AI agents. Every security-sensitive action an agent takes is checked immediately before execution and either allowed, blocked, or held for a human. The decision is bound to a short-lived signed permit, so the action cannot happen any other way.

The problem

Agents moved from answering to acting. Security did not move with them.

Once an agent can read secrets, run shell, call tools, change business data, spend money, or delegate to other agents, the question is no longer "is the model safe?" It is "is this exact action authorized right now?" Nothing in today's stack answers that question at the moment it matters — immediately before execution.

Intent integrity

Emails, web pages, documents and tool outputs can redirect an agent toward an attacker's goal. And no attacker is needed — an agent can confidently choose a destructive action on its own.

Validate the planned effect, not the model's confidence

Identity mistaken for authority

A valid token proves who is calling. It does not prove that this refund, this delete, this export is allowed. Agents inherit broad service accounts and user permissions by default.

Authorize the action, resource and arguments

Execution boundary

IDE and CLI agents sit next to files, shell, Git, credentials and the network. A wrong instruction moves from text to real execution in one step.

Gate file, process and network primitives

Tool and protocol control

MCP authenticates the connection. It does not decide whether this agent, for this user, may call this tool with these arguments. Valid credentials still permit misuse.

Semantic policy on tool + args + destination

Delegation and humans

Subagents inherit their parent's power. Approving every command creates fatigue; approving none creates unacceptable autonomy. Nobody can say which human authorized the final effect.

Attenuate authority; bind approvals to exact actions

Fragmented control plane

AWS, Microsoft, Google, Salesforce and ServiceNow each ship their own policy model. Logs tell you what happened after the fact. Nothing stops the action across vendors.

One normalized action model, enforced before execution

What we are building

A deterministic gate between an agent's decision and the real-world effect.

Wrapbox does not govern AWS, GitHub or Stripe. It governs an agent attempting an AWS, GitHub or Stripe action — before that action executes. Three questions, every time: what is the agent, where can we intercept, what is it trying to touch.

One authorized effect, end to end

A custom insurance claims agent requests an ₹3,00,000 payout. This is the flow we demo.

Register the agent

The platform lead registers claims-agent-prod with its owner, environment and identity. The team wraps the payout tool with the Wrapbox SDK, or routes it through an Wrapbox MCP gateway.

Map the resource and set policy

Wrapbox learns pay_claim moves real money. Policy: up to ₹25,000 allow; ₹25,001–₹2,00,000 review; above ₹2,00,000 requires two-person review.

The agent decides to act

The model calls pay_claim(claim_id=4821, amount=300000). Wrapbox receives the human delegator, agent identity, tool, exact arguments, environment and purpose.

Deterministic decision

The policy engine returns REVIEW. The LLM cannot override the result by arguing the claim is urgent. No model reasoning participates in the decision.

Human step-up with context

Two claims managers see amount, customer, reason, agent, originating user, the policy that fired, and a dry-run of what will change. Approval is bound to this exact request — not to "the agent" in general.

Permit issued

Wrapbox mints a short-lived, non-replayable permit for only this action, target and amount. It expires in 60 seconds. It is not a payments credential.

Effect enforced at the executor

The payment service verifies the permit immediately before calling the payment API. If the agent changes the amount to ₹3,50,000, the args hash no longer matches and the call fails. No valid permit, no execution.

Evidence recorded

Human → agent → tool → resource → policy → approver → permit → outcome. SOC and GRC can reconstruct the decision months later.

The non-negotiable rule: hooks, plugins and SDK calls are integration adapters, not security boundaries. For high-risk effects the executor, gateway or target service must require a verifiable permit — so bypassing an optional hook does not silently grant authority.

How it works

One intent contract. Every agent reads it.

A company writes what its agents may do once, in one file. Wrapbox translates that contract into whatever each agent understands — a Claude Code hook, a Cursor hook, an SDK guard, an MCP gateway — and answers every action in the agent's own format. Three steps.

1

Write the intent contract

Plain rules about effects and resources — not about any one tool. Reads are first-class. Amounts, branches, environments and approvers are all in the same vocabulary. Committed to the repo or set org-wide from the control plane.

Proposed Wrapbox schema. This is our design, not a vendor's.

wrapbox.yaml
# One contract for every agent in the org
version: 1
org: acme

resources:
  secrets:     ["**/.env*", "**/*.pem", "**/id_rsa*"]
  production:  { env: production }

rules:
  # Sensitive reads are policy events, not just writes
  - effect: filesystem.read
    resource: secrets
    decision: BLOCK

  - effect: git.push
    branch: main
    decision: BLOCK

  - effect: shell.exec
    match: "kubectl delete * -n prod"
    decision: REVIEW
    approvers: [oncall-sre]
    permit_ttl: 60s

  - effect: payments.refund
    tiers:
      - amount: { lte: 500 }   decision: ALLOW
      - amount: { lte: 5000 }  decision: REVIEW
      - amount: { gt: 5000 }   decision: BLOCK

  - effect: agent.delegate
    attenuate: true   # child never exceeds parent

default: ALLOW   # low-risk work stays automatic

Each platform already exposes a pre-execution hook or a place to wrap tool calls. Wrapbox plugs into the one it has. Nothing here is invented — every field below is from the vendor's current documentation.

What the policy engine normalizes

Twelve action classes. One canonical schema across every integration, so a rule about reading secrets applies equally to cat .env, an MCP get_secret, a REST call to /secrets, and a subagent that tries the same thing.

  • Filesystem read — .env, SSH keys, customer exports, source
  • Filesystem write / delete — config edits, directory deletes, secret overwrites
  • Process / shell — bash, python, kubectl, terraform, argv and cwd
  • Git / repository — commit, push, branch, merge, PR, protected branches
  • MCP tool call — server, tool, arguments, principal, target
  • API / SaaS — method, route, customer, business threshold
  • Database — SELECT vs UPDATE/DELETE/DROP, table class, row count, environment
  • Cloud / IAM — role creation, VM deletion, security group changes, blast radius
  • Payments / commerce — amount, payee, currency, dual approval
  • Email / messaging — recipient domain, bulk send, sensitive content
  • Browser / computer — semantic action, target site, irreversibility
  • Agent delegation — what authority may travel, expiry, downstream tools

Reads are first-class

A security model that only checks side effects misses the exfiltration paths that actually get exploited — secrets, credentials, source code, customer records. Wrapbox governs security-sensitive I/O, not only writes. This is one of the concrete places where existing gateways fall short.

Same effect, many routes

Reading a secret can happen through filesystem APIs, shell, MCP, REST, browser, or a subagent. Route-specific rules leave bypasses. Wrapbox normalizes equivalent effects and enforces at the lowest practical boundary — which is why the endpoint runtime exists alongside hooks.

Deterministic, not model-judged

AI may help author or explain a policy. Enforcement is deterministic and reviewable. A model that can be argued into a decision is not a security boundary.

The technical wedge

The permit is the primitive. Everything else compounds around it.

"Runtime security for AI agents" is not unique in 2026 — AWS, Microsoft, Google, Salesforce, ServiceNow, Palo Alto and a handful of startups each address a slice. That is market validation. Wrapbox has to own a narrower, stronger invariant: a sensitive effect cannot occur unless the final enforcement point verifies a short-lived authorization bound to the exact action.

What a permit contains

subject_agent_idwhich agent is authorized
human_or_delegator_idwhose authority the agent is using
action_fingerprintexact command, tool or API action
resource_fingerprintexact path, record, account
canonical_args_hashstops amount, payee, path or command changing after approval
scope / environmentrepo, project, prod or staging, tenant
decision_idlinks to policy evaluation and evidence
issued_at / expires_atseconds, not sessions — shrinks the replay window
nonceone-time use where needed
signatureexecutor verifies without calling home

Why this beats a hook: a hook can say "approved," but if the executor does not require proof, another code path bypasses it. A permit lets the protected executor refuse anything that does not carry a valid proof for this exact operation.

Five things we build that we did not find together anywhere else

  1. Effect-level enforcement on local endpoints — file, process and network primitives below the agent's planner, not only inside it.
  2. MCP, API and agent-to-agent enforcement under one normalized action schema and one policy language.
  3. Exact-operation signed permits with args hashing, short expiry and replay protection, verifiable by the resource server.
  4. Delegation lineage with attenuation — a child agent never receives broader authority than its parent granted, and the human at the root is always recoverable.
  5. Policy simulation and replay — change a rule, replay last quarter's real actions, see what would newly block before you turn enforcement on.

Honest assurance levels

We will label every integration by what it can actually guarantee — observe-only, hook-enforced, gateway-enforced, endpoint-enforced, resource-verified. Customers get an assurance score per agent, and a roadmap to raise it. Selling less than you can prove is how you lose a security customer forever.
