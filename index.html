The problem

Agents stopped answering and started acting. Security did not move with them.

In 2026 an AI agent on a developer laptop can read credential files, push to production, call payment APIs and message customers. The attack that matters is no longer "the model said something bad." It is the model did something real, milliseconds after reading a poisoned web page.

One click, full takeover
CVE-2026-25253 in OpenClaw: a single malicious link let an attacker take over the agent host through a missing gateway check. Agent frameworks became remote-execution surfaces.
The supply chain came for agents
The ClawHavoc campaign seeded hundreds of malicious agent skills and MCP packages. Installing an agent extension is now the same trust decision as installing a kernel driver, made by interns.
Exfiltration through an allowed channel
Anthropic's own containment write-up documents an agent tricked into leaking data through its legitimately-allowed file API. The lesson from the vendor closest to the models: put enforcement in the environment, not in the model's judgement.
Approval fatigue is measured, not anecdotal
In Anthropic's published data, users waved through roughly 93% of agent permission prompts. A dialog box is not a control. Deterministic policy plus rare, well-argued human review is.
The standards bodies named the gap
OWASP shipped an Agentic Security Top 10. NIST published an agent-identity concept paper in February 2026. Buyers now have a checklist and no single vendor-neutral product that answers it.
Security teams tried per-agent glue
A hook for Claude Code, a plugin for Cursor, a config for each MCP server. Every new agent means new work, and the unknown script that appeared yesterday is covered by nothing at all. Integration-by-integration security loses to agent adoption speed. Always.
The product

Two pieces of software. One application. One contract between them.

Wrapbox ships the way an EDR ships, not the way an SDK ships. IT installs the Runtime on every machine and the Gateway on the network once. From then on, governance of any agent, present or future, is configuration, never engineering.

Every action, one shape, four answers

Whatever the source: a shell command, a file read, an MCP tool call, a refund. The enforcement point normalizes it into one Act, with three fields nobody else attaches: launch_mode (was this agent started under governance?), provenance.source (which sensor saw it?) and device.id. One engine evaluates it against one contract. The most restrictive matching rule wins. Missing context does not fall through: it fails closed.

ALLOW  proceed  ·  CONSTRAIN  rewrite it safely (mask PII, swap in a brokered key)  ·  REVIEW  a named human signs, with a dry-run in front of them  ·  BLOCK  refused, and the reason goes back to the model so it adapts instead of retrying.

Why the unknown agent is the whole point

Next quarter, agent #64 arrives and three hundred engineers install it on their own. Nobody files a ticket. With per-agent security, that agent is invisible until someone builds an integration. With Wrapbox, the Runtime's floor already sees the new process, notices no profile matches it, and one seeded rule does the rest:

# wrapbox.yaml · rule shipped in the default contract
- id: model.egress
  title: "Only managed agents may reach a model provider"
  when: { effect: model.request }
  requires: agent.launch_mode in [wrapbox, native-managed]
  otherwise: BLOCK  # unknown or tampered → no model calls

Ungoverned agents lose their brain until they are enrolled. That single behavior converts shadow AI from a discovery problem into a non-event.

The laptop caught it

The Runtime sits under the agent at the OS layer. The credential read was stopped before the file opened, not flagged after. And the reason went back to the model, so it explained itself instead of retrying forever.

The network had nothing to steal

The subtler attack, exfiltrating through an allowed API, dies differently: the agent never held a real key. The Gateway brokers a five-minute credential scoped to one task. Stealing it buys an attacker almost nothing, briefly.

The deploy needed a receipt

The push to main required an approval signed with a passkey, minted into a 60-second single-use permit that the git service verified itself. Disable the Runtime, and you still cannot deploy: no receipt, no effect.

One contract

Rules a CISO can read. A file an engineer can diff.

Eighteen rules govern the reference tenant today: secrets, egress, protected branches, production deletes, PII masking, refund tiers, delegation limits, adapter integrity. Both views below are the same object. Change one, the other updates, and you can replay the last 20,070 real decisions against your draft before publishing.

# One contract for every agent in the org · published by Maya, 3d ago
version: 27
default: ALLOW   # most restrictive matching rule wins · missing context fails closed

- id: secrets.read
  when: { effect: filesystem.read, path: ["**/.env*", "**/*.pem", "**/id_rsa*"] }
  decision: BLOCK          # reads are first-class: exfiltration starts with a read

- id: git.main
  when: { effect: git.push, branch: [main, master] }
  decision: REVIEW  approvers: oncall-sre  permit: { ttl: 60s, single_use: true }

- id: payments.refund       # same rule for Stripe MCP, Razorpay MCP, SDK or raw REST
  tiers: [ ≤$500 → ALLOW,  ≤$5,000 → REVIEW(payments-manager),  above → BLOCK ]

- id: runtime.integrity
  when: { effect: runtime.integrity }   # adapter edited outside Wrapbox
  decision: BLOCK   # agent reclassified unmanaged, adapter rewritten, both events recorded
Secret files are never read autonomously.
Because exfiltration starts with a read, not a send.

Pushes to main need the on-call engineer and carry a receipt.
GitHub refuses any push to a protected branch without a valid permit.

Refunds: up to $500 flow, up to $5,000 a payments manager signs, above that no.
Any route: MCP, SDK, REST. Currency normalized before evaluation.

A changed adapter is rejected and rewritten.
Tampering does not disable Wrapbox. It disables the agent.

Deterministic by design: no model sits in the allow/block path. A model may help draft a rule; a person publishes it; the engine that decides is plain code with a trace you can read per decision.

Honest assurance

Four coverage classes. Gaps are stated, never hidden.

Security products fail when they imply uniform protection they cannot deliver. Wrapbox shows, per agent and per action kind, exactly which guarantee applies, and says so plainly when one is missing. Buyers trust the product because the Fleet page refuses to flatter them.

endpoint-enforced

The primitive

A receipt the destination checks itself.

An approval is not a click. It is a passkey signature over the exact arguments, minted into a short-lived, single-use, ES256-signed permit. Under the hood

What is actually inside the two pieces of software.

This is the engineering reality the budget pays for — written for a founder who is about to hire the team that builds it, and for the engineers who will judge it. Each component below maps to a role in the plan. Nothing here is hand-waving: every mechanism named is the standard, shipping way to do this on that operating system.

Wrapbox Runtime — anatomy of wrapboxd

One core binary (Go, statically linked, ~15 MB) that is identical on every OS, plus a thin enforcement shim per platform. The policy engine inside it is the same evaluate() that runs in the Control Plane and the Gateway — one engine, compiled three times, never three implementations.

1 · Sensor and confinement layer (the per-OS part)

macOSEndpoint Security ext · Network Extension filter · Seatbelt profiles
 signed + notarized · MDM mobileconfig (SysExt, PPPC, Filter)
LinuxeBPF on LSM hooks · seccomp-bpf · namespaces + cgroup v2
 built on Anthropic's open-source sandbox runtime · nftables redirect
Windows · comingWFP user-mode filters · restricted token launch · no kernel driver in v1

This layer answers one question fast: which process, started by whom, is touching which file, socket or child process. It sees the attempt before the OS completes it. That is the Floor.

2 · Discovery and adapter provisioner

Reads agent profiles (data files: binary names, signing IDs, config paths, adapter template, model endpoints), finds what is installed, and writes each agent's native hook file itself — managed-settings.json, hooks.json. An integrity watcher (FSEvents on macOS, inotify on Linux) sees any outside edit: the agent is reclassified as unmanaged, the file is rewritten, both events land in evidence. Supporting agent #64 is a new profile, zero new code.

3 · Local evaluator + signed policy cache

The published contract arrives as a signed bundle (v27 today) and is cached on disk, so decisions are local and take milliseconds, and a laptop on a plane keeps enforcing. Offline behavior is tiered: routine work continues, receipt-tier actions fail closed until the device checks in again.

4 · Egress proxy, evidence spool, identity

A loopback proxy applies domain policy and the model-egress gate, and carries brokered calls to the Gateway over mTLS. Every decision appends to a local append-only log where each record carries the hash of the previous one, then syncs in batches. The device's own identity is a keypair born in the Secure Enclave (Mac) or TPM (Linux/Windows) — it never leaves the chip. Heartbeat every 30 s; a signed updater with staged rollout and rollback completes the loop.

Wrapbox Gateway — anatomy of the front door

First, the name, because it confuses everyone once: this is a network gateway — one controlled door for traffic — not a payment gateway. Payment gateways such as Stripe and Razorpay are among the services it wraps. It is a stateless Go service shipped as a container: docker run for the fast path, Helm with replicas for production, Postgres for configuration and evidence buffering, Redis for sessions and one-time nonces. Scale it like any web service.

1 · Virtual MCP server

Speaks the MCP protocol to any client and aggregates your real upstream MCP servers behind one URL per service (mcp.wrapbox.ai/stripe). Each upstream tool's schema is pinned by hash — if a tool's definition changes upstream (a classic supply-chain move), calls to it drop to REVIEW until a human re-approves the new shape.

2 · Forward API proxy + normalizer

Plain REST and SDK traffic goes through the same door. The normalizer maps every call to one effect vocabulary — a Stripe refund and a Razorpay refund both become payments.refund — which is why one rule governs any route and any currency.

3 · Credential broker (the part that removes stolen keys as a category)

Real secrets stay in your vault (HashiCorp Vault, AWS KMS, cloud secret managers) and are referenced by id only — no secret value exists in Wrapbox config, code or logs. Per approved session it issues a short-lived token bound to agent + device + scope + TTL, strips whatever Authorization header the agent sent, and injects the brokered credential on the way out. Revoke is a click; the very next call with that token is refused.

4 · Policy point, receipts, evidence stream

The same engine and the same published contract as every device, so a refund rule written once holds at the laptop and at the network. Receipt-tier calls carry the ES256 permit through to destinations, which verify it against the public key set (kid wbx-2026-09). Every decision streams to the evidence store and out to your SIEM in standard shapes.

Real, working now

  • The policy engine: every decision on every screen is computed live by evaluate(), with a per-rule trace saying why each rule matched or did not
  • ES256 permits: minted and verified with WebCrypto ECDSA P-256. The tamper and replay demos fail through the real verifier
  • One Rule schema round-tripping between plain English, a builder and YAML, with versioned history and draft-vs-live replay over 20,070 decisions
  • Hash-chained evidence records (prev_hash) with export shapes for Splunk and Datadog
  • State machines with teeth: device enrolling→healthy→heartbeat-lost→quarantined; adapter provisioned→tampered→re-provisioned; a quarantined device cannot mint receipts
  • The unknown-agent path end to end: an unenrolled script's model calls land BLOCK by rule evaluation, visibly, with the failed condition named

Simulated, honestly labelled

  • The agents themselves and their traffic (replayed, deterministic)
  • The Runtime and Gateway as installed binaries: real commands and screens, nothing actually installs yet. Building them is the plan and the budget below
  • SSO, MDM push and the secrets vault behind the broker
  • Downloads and docs pages serve real commands and real prose; the artifacts are placeholders until MVP-1

We keep this split on the page because the buyers we want, security engineers, punish vagueness and reward exactness. So do the investors we want.

Why now, why us

Every piece is validated by an incumbent. The combination is owned by nobody.

This is not a bet that the category exists. Microsoft Defender now discovers and protects local coding agents through hooks. Sysdig detects risky agent behavior. AWS AgentCore enforces default-deny policy at its own gateway. Okta shipped agent SSO. A dozen startups broker MCP credentials. Anthropic open-sourced the sandbox itself. Each of them proves one layer, inside one vendor's walls.

The unowned position

Nobody ships, as one vendor-neutral product: the device floor, plus auto-provisioned hooks, plus gateway credential brokering, plus destination-verified receipts, under one policy language and one evidence chain, for every agent at once. That is the whole product. Platform vendors will not build it because each protects only its own agents; that conflict is structural, and it is our room to run.

The window is real but not lazy: parts of it close with a feature release from Redmond or Austin. Our moat is therefore speed of coverage (a new agent is a profile file, not a project), the receipt workflow destinations adopt, and the evidence format auditors start asking for by name.

Who pays, and for what

The buyer is the CISO of a company whose engineers already adopted agents. The trigger is an audit, an incident or a board question: "what can these things actually do, and who approved it?" Wrapbox is the first product that answers with a device count, a rule file and a signed evidence chain instead of a policy PDF.

Pricing follows the shape of the product: per governed device for the Runtime, per gateway plus decision volume for the Gateway, platform tier for SSO, SIEM, receipts-at-destination and compliance packs. Developer-led entry through the free tier and the Gateway alone, which stands as a product by itself.

The plan

No single final release exists. Every rung is a product on its own.

The build is a ladder. If any rung slips, the one below it is still a business. Two written kill conditions at day 90 decide whether the serious money gets spent at all.

The Control Plane prototype

Deployed, QA'd screen by screen, real engine and real crypto inside. It is the sales asset for design partners and the spec for everything below.

Built on Anthropic's open-source sandbox runtime rather than new kernel code: confinement, model-egress gate, adapter provisioning, evidence sync. Runs on developer Linux machines and CI. Two or three design partners live.

Kill conditions, written down in advance

Stop the company at day 90 if either fails: (1) the two senior systems engineers, macOS and Linux, are not hired and delivering. (2) Fewer than two real companies are running the pilot on real machines. Pass both, raise and continue. Investors get this honesty in the deck, not discovered later.

macOS beta + receipts in the wild

macOS Runtime via the Network Extension path while Apple's Endpoint Security entitlement (filed in week 1) is pending. And the single most convincing demo in the category: a GitHub App that refuses any push to main without a valid Wrapbox receipt, live at a pilot customer.
